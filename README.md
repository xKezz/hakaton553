# Система оптимизации возврата клиентов и управления их вовлечённостью на основе поведенческих данных

Бот для мессенджера MAX, который помогает малому бизнесу возвращать ушедших
клиентов через персональные бонусы.

---

## 1. Назначение решения

Решение анализирует историю покупок малого бизнеса и возвращает клиентов с
помощью персональных бонусных предложений в мессенджере MAX.

Что делает продукт:

* принимает от бизнеса CSV с историей покупок;
* накапливает историю в PostgreSQL (повторные загрузки не создают дублей);
* считает RFM-аналитику по **всей** накопленной истории;
* объединяет 27 RFM-комбинаций в 5 маркетинговых групп;
* предлагает размер бонуса для каждой группы;
* даёт администратору скорректировать бонус и запустить кампанию;
* рассылает персональные предложения клиентам в MAX;
* по окончании кампании считает, кто вернулся, и отзывает неиспользованные
  бонусы;
* показывает отчёт по кампании и выгружает историю всех кампаний в CSV.

## 3. Состав и архитектура решения

```
CSV бизнеса
    ↓
src/data_process/loader.py          ColumnFinder - поиск колонок
src/data_process/predprocessing.py  Preprocessor - нормализация
src/pipeline.py                     Pipeline.run(): сохранение истории, 
                                    аналитика, создание кампании
    ↓
src/segmentation/business_metrics.py   метрики (recency/frequency/monetary)
src/segmentation/user_categories.py    27 RFM-комбинаций => группы
src/segmentation/full_categorised.py   сборка отчёта по бонусам
src/recommendations/bonus_policy.py    размеры бонусов
    ↓
src/DB/models.py        Client / Purchase / Campaign /
                        CampaignCategory / CampaignTarget
src/DB/crud.py          запросы и запись
src/DB/database.py      async engine + async_session (PostgreSQL)
    ↓
src/Bot/bot.py          MAX-бот: меню, FSM, кампании, рассылка,
                        time-machine (asyncio-задача внутри процесса)
    ↓
src/services/loyalty_mock.py   CSV-эмулятор программы лояльности
                               (балансы, визиты, списания)
```

| Файл                                          | Роль                                                                                                               |

## 10. Описание работы с данными

**Входные данные.** CSV с покупками. Имена колонок могут отличаться -
`ColumnFinder` сам находит ID покупки, телефон, дату и сумму. 

**Обработка (`Pipeline.run`).**

1. Определяются колонки.
2. `Preprocessor` нормализует данные: телефон => E.164, дата => `YYYY-MM-DD`,
   сумма => число.
3. Новые покупки сохраняются в PostgreSQL; дубликаты по `purchase_id` не
   создаются.
4. Из БД берётся **вся накопленная** история покупок.
5. Аналитика пересчитывается по всей истории: метрики => 27 RFM-комбинаций =>
   5 маркетинговых групп => бонусы.
6. Создаются `Campaign` (статус `DRAFT`), `CampaignCategory` (5 групп) и
   `CampaignTarget` - только для групп 0–3 и только с бонусом > 0.
7. Исходный файл сохраняется в `data/source_files/<uuid>_<имя>.csv`; при
   ошибке обработки он удаляется.

**Хранение.** PostgreSQL, 5 таблиц (`create_db.sql`):

| Таблица             | Содержимое                                                   |
| ------------------- | ------------------------------------------------------------ |
| `client`            | телефон в программе лояльности + MAX user_id                 |
| `purchase`          | вся накопленная история покупок                              |
| `campaign`          | кампания: статус, срок, файл-источник, счётчики, JSON-конфиг |
| `campaign_category` | 5 групп: метрики, предлагаемый и итоговый бонус              |
| `campaign_target`   | конкретные клиенты кампании: бонус, факт реализации          |

**Бонусы.** Значения по умолчанию: группа 0 => 300, группа 1 => 200,
группа 2 => 100, группа 3 => 50, группа 4 => 0. Шаг изменения +-50, границы
0…300. Группа 4 бонус не получает.

**CSV-эмулятор лояльности** (`data/loyalty_mock/`) (*файлы генерируются сами при первом начислении бонусов*):

| Файл | Что содержит |
|---|---|
| `transactions.csv` | журнал операций: `ACCRUAL` (начисление), `REDEMPTION` (списание), `REVOKE` (отзыв), `OPENING` (старый баланс). Баланс клиента = сумма операций |
| `visits.csv` | эмулированные визиты: дата, сумма чека, сколько бонусов списано |
| `balances.csv` | производный снимок балансов «для глаз» (логикой не читается) |

У клиента **один общий баланс**. Аналитика кампании считается отдельно:
`bonus_realised` = сумма списанных бонусов за период кампании, но не больше
`bonus_amount`. Значение зеркалится в `campaign_target.bonus_realised`.
Эмуляция детерминированная (seed) и переживает перезапуск бота.

**Персональные данные.** Телефоны и MAX user_id маскируются в логах
(`***4567`). Бизнес-данные хранятся в PostgreSQL, а не в логах.

## 11. Порядок работы с тестовыми данными

1. **Автотесты не требуют файлов**: фикстуры генерируются в
   `tests/conftest.py`, БД - sqlite in-memory. Достаточно `./run_tests.sh`.
2. **Ручная проверка бота**: используйте
   `data/source_files/real_test_with_purchase_id.csv` (~5,5 тыс. покупок).
   Отправьте его боту в MAX как документ.
3. **Проверка на своём файле**: подойдёт любой CSV, где есть ID покупки,
   телефон, дата и сумма (лимит файла - 30000 строк)
4. **Сброс эмулятора лояльности** (обнулить балансы и историю визитов):

   ```bash
   rm -rf data/loyalty_mock/
   ```

   Каталог будет создан заново при первом начислении.
5. **Быстрая проверка завершения кампании**: поставьте в `.env`
   `CAMPAIGN_FINISH_CHECK_INTERVAL=5`, чтобы time-machine срабатывал каждые
   5 секунд.
6. **Полный сброс БД** (удалить накопленную историю и кампании):

   ```bash
   sudo -u postgres psql -d winback_db -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"
   sudo -u postgres psql -d winback_db -f create_db.sql
   ```

## 12. Пошаговый сценарий проверки

### Основной сценарий: Docker

**Шаг 1. Подготовить окружение**

```bash
cp .env.example .env
```

**Шаг 2. Заполнить `.env`** - `MAX_BOT_TOKEN` и DATABASE_URL! В `.env.example` - значения-заглушки.

**Шаг 3. Запустить все локальные компоненты одной командой**

```bash
sudo docker compose up -d
```

**Шаг 4. Открыть бота в MAX** и отправить `/start`. Вы клиент => появится поле ввода/отправки номера, затем меню пользователя с полями доступных бонусов и спец. предложений.

**Шаг 5.  ВАЖНО: после первого /start в роли клиента для доступа к админ-панели, необходимо заполнить ADMIN_IDS в .env. Его можно получить из логов, вписав команду в терминал**:

```bash
sudo docker compose logs bot | grep -A1 '\[/start\]'
```

После ввода ADMIN_IDS, повторный запуск с доступом к админ-панели:

```bash
sudo docker compose up -d --force-recreate
```


**Шаг 6. Загрузить CSV** кнопкой «Загрузить CSV» (или просто отправить документ в чат).
Бот покажет 5 групп с метриками и бонусами.

**Шаг 7. Скорректировать бонус.** «Категории» => выбрать группу => кнопки
`[−50] [текущий] [+50]`. Границы 0…300; у группы 4 бонуса нет.

**Шаг 8. Запустить кампанию.** «Запустить кампанию» => «Подтвердить».
Статус становится `APPROVED`, клиентам уходят предложения.

**Шаг 9. Дождаться завершения кампании.** По умолчанию срок - 30 дней. Для
быстрой проверки задайте конец кампании в прошлом прямо в контейнере:

```bash
sudo docker compose exec db psql -U postgres -d winback_db \
  -c "UPDATE campaign SET campaign_ends_at = now() - interval '1 minute'
      WHERE status = 'APPROVED';"
```

В течение `CAMPAIGN_FINISH_CHECK_INTERVAL` секунд (по умолчанию 60) бот
завершит кампанию, отзовёт неиспользованные бонусы и пришлёт админу отчёт.

**Шаг 10. Выгрузить историю.** Кнопка «Выгрузить историю кампаний (CSV)»
пришлёт файл со сводкой по всем кампаниям.

**Шаг 11. Прогнать автотесты** (локально - тесты не входят в Docker-образ)

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
./run_tests.sh 
```

### Альтернатива: локальный запуск через `setup.sh`

Если Docker недоступен, проект разворачивается:

```bash
./setup.sh
venv/bin/python -m src.Bot.bot
```

`setup.sh` ставит PostgreSQL, создаёт роль `postgres` и БД `winback_db`,
применяет схему `create_db.sql`, поднимает `venv` с зависимостями из
`requirements.txt`, создаёт `.env` из `.env.example` и проверяет
подключение к БД. Шаги 4–11 проверки - те же; отличается только правка
срока кампании (выполняется на хосте):

```bash
sudo -u postgres psql -d winback_db \
  -c "UPDATE campaign SET campaign_ends_at = now() - interval '1 minute'
      WHERE status = 'APPROVED';"
```

## 14. Известные ограничения

1. **Один бот = один бизнес.** Мультитенантности нет; список администраторов
   задаётся `ADMIN_IDS`.
2. **Loyalty API эмулируется CSV.** Реальной интеграции с программой
   лояльности нет: балансы и «возвраты» клиентов генерирует
   `src/services/loyalty_mock.py`. `bonus_realised` - атрибуция эмулятора,
   а не доказанный causal return.
3. **Строка подключения зашита в код.** `src/DB/database.py` использует
   `postgres:postgres@localhost:5432/winback_db`. Из-за этого контейнер бота в `compose.yaml` работает в
   `network_mode: host` - **Docker-запуск рассчитан на Linux** (на macOS и
   Windows host-сеть недоступна). Чтобы убрать ограничение, достаточно
   научить `database.py` читать `DATABASE_URL`.
4. **Конфликт порта 5432.** Локальный PostgreSQL из `setup.sh` и контейнер
   `db` используют один порт. Перед `docker compose up` остановите локальный:
   `sudo service postgresql stop`.
5. **Предел размера CSV.** Не более 30 000 строк: в `src/DB/crud.py` запросы
   `IN (...)` не разбиты на чанки, а asyncpg допускает 32 767 параметров.
6. **Рассылка отправляется один раз.** Кнопки повторной рассылки нет
   (защита от двойного начисления). Если MAX не принял сообщение, начисление
   откатывается, но автоповтора нет.
7. **Просроченную кампанию нельзя запустить «в пустоту»**: при попытке
   запуска срок автоматически продлевается на `CAMPAIGN_DAYS`.
8. **Время - naive UTC.** Если править `campaign_ends_at` в БД вручную в
   локальном времени, кампания завершится позже на величину смещения
   часового пояса.
9. **Данные не удаляются автоматически**: кампании и история покупок
    накапливаются; чистка - вручную

## 15. Порядок остановки и повторного запуска

### Docker

| Действие                            | Команда                        | Данные                             |
| ----------------------------------- | ------------------------------ | ---------------------------------- |
| Запустить всё                       | `docker compose up -d`         | сохраняются                        |
| Остановить, не удаляя               | `docker compose stop`          | сохраняются                        |
| Остановить и удалить контейнеры     | `docker compose down`          | том `pgdata` и `data/` сохраняются |
| Перезапустить после простоя         | `docker compose up -d`         | продолжают с прежнего состояния    |
| Пересобрать образ после правок кода | `docker compose up -d --build` | сохраняются                        |
| Посмотреть логи                     | `docker compose logs -f bot`   | -                                  |
| Статус                              | `docker compose ps`            | -                                  |
| Полный сброс (удалить и БД)         | `docker compose down -v`       | **том БД удаляется**               

### Локальный запуск (setup.sh + venv)

**Остановить бота:** `Ctrl+C` в терминале. Бот корректно завершает
time-machine и фоновые задачи; состояние остаётся в PostgreSQL и
`data/loyalty_mock/`.

**Повторный запуск:**

```bash
venv/bin/python -m src.Bot.bot
```

**Остановить PostgreSQL (если нужно освободить порт 5432):**

```bash
sudo service postgresql stop     # или: sudo systemctl stop postgresql
```

**Снова поднять после перезагрузки (WSL/без systemd):**

```bash
sudo service postgresql start
venv/bin/python -m src.Bot.bot
```



После любого перезапуска бот продолжает работу с накопленным состоянием:
история покупок и кампании - в PostgreSQL, эмулятор лояльности - в
`data/loyalty_mock/`. Просроченные кампании (статус `APPROVED` и истёкший
`campaign_ends_at`) будут завершены в течение
`CAMPAIGN_FINISH_CHECK_INTERVAL` секунд после старта.
