## 1. Контекст и цель проекта

### 1.1. Продуктовая цель

Создать MVP-продукт для малого бизнеса, решающий проблему оттока клиентов (win-back стратегия) через механику **сгораемых бонусных баллов**, начисляемых в существующую систему лояльности бизнеса.

### 1.2. Платформа

- **Мессенджер:** российский мессенджер MAX (поддержка ботов и мини-аппов)
- **Бот:** первичная регистрация пользователя + push-уведомления о бонусах
- **Мини-апп (для бизнеса):** весь основной интерфейс — загрузка данных, просмотр предложений, редактирование, подтверждение, аналитика
- **Мини-апп (для клиента):** НЕ разрабатывается в MVP (опущено по решению)

### 1.3. Ограничения MVP

| Ограничение | Пояснение |
|---|---|
| Один бизнес | Пилотный проект, мульти-тенантность не нужна |
| Без дашбордов | Только текстовая аналитика и отчёты через бота |
| Без ML | Малый объём данных, используем правило-ориентированный подход |
| Минимум внешних API | Только API лояльности бизнеса и MAX Bot API |
| Объём данных | До 200 000 строк в CSV |
| Срок | 4 дня на реализацию |

### 1.4. Базовый алгоритм (уже реализован)

Существующий Python-пайплайн:

- Рассчитывает клиентские метрики (RFM: recency, frequency, monetary_score)
- Строит матрицу сегментов 3x3x3 = 27 базовых групп
- Разбивает на `count_cat` маркетинговых категорий
- Рассчитывает предложенный бонус для каждой категории
- Формирует JSON-отчёт с `meta`, `categories`, `clients`

### 1.5. Структура существующего проекта

```
.
├── business_metrics.py      # Загрузка данных и расчёт метрик
├── user_categories.py       # Матрица сегментов и назначение категорий
├── discount_policy.py       # Расчёт скидки (→ переписать под бонусы)
├── pipeline.py              # Оркестрация и формирование JSON-отчёта
├── requirements.txt         # pandas>=2.0.0, numpy>=1.26.0
└── main.py                  # Точка входа
```

### 1.6. Формат входных данных (CSV)

| Колонка | Тип | Описание |
|---|---|---|
| `client_id` | строка | Идентификатор клиента (сохраняет `+`, ведущие нули) |
| `purchase_date` | дата | Дата покупки (формат `YYYY-MM-DD`) |
| `amount` | число | Сумма покупки |

Пример:

```
client_id,purchase_date,amount
+79991234567,2026-05-01,390.0
+79991234567,2026-06-01,450.0
+79997654321,2026-04-15,1200.0
```

### 1.7. Клиентские метрики (из пайплайна)

Для каждого клиента рассчитываются:

| Метрика | Описание |
|---|---|
| `recency` | Количество дней с момента последней покупки |
| `frequency` | Количество покупок |
| `total_amount` | Общая сумма покупок |
| `avg_amount` | Средний чек |
| `monetary_score` | Комбинированный нормированный показатель ценности (0.0–1.0) |

### 1.8. Матрица сегментов

- 3 уровня recency x 3 уровня frequency x 3 уровня monetary_score
- Максимум 27 базовых групп
- Для `win-back`: чем дольше клиент не покупал и чем выше его ценность, тем выше приоритет
- Категория `0` — самая приоритетная

## 2. Противоречия и их разрешение

### 2.1. Скидки (%) vs Бонусные баллы

| Было | Стало | Решение |
|---|---|---|
| Алгоритм рассчитывает `discount` в % | Переходим на бонусные баллы | Переписываем формулы `discount_policy.py` в `bonus_policy.py`. `max_discount` заменяется на `max_bonus_points`, `step` на шаг в баллах |

### 2.2. Интеграция с программой лояльности

| Было | Стало | Решение |
|---|---|---|
| «Использование сторонних API сильно ограничено» | Требуется доступ к API лояльности бизнеса | Требуем у бизнеса доступ к их API программы лояльности. Проектируем идемпотентные запросы. Допускаем, что сервис «хороший» и поддерживает вебхуки |

### 2.3. Админка = Мини-апп

| Было | Стало | Решение |
|---|---|---|
| Неясно: веб-админка или мини-апп | Всё происходит в мини-аппе MAX для бизнеса | Мини-апп — единственный интерфейс для бизнес-пользователя. Веб-интерфейс разрабатываем с нуля |

### 2.4. Механизм сгорания баллов

| Было | Стало | Решение |
|---|---|---|
| Не определено кто и как списывает баллы | Алгоритм сгорания в нашей системе | Реализуем Scheduler, который отслеживает TTL и вызывает API лояльности на списание |

### 2.5. Редактирование предложений

| Было | Стало | Решение |
|---|---|---|
| Неясно: точечное или массовое | Бизнес меняет **массовые правила для групп** | Бизнес видит 3–27 карточек категорий и редактирует бонус на уровне категории. Не трогает отдельных клиентов |

## 3. Архитектурные решения

### 3.1. Загрузка CSV

- **Метод:** `POST /api/v1/campaigns/upload` (multipart/form-data)
- **Ограничение размера:** до 50 МБ на уровне реверс-прокси / фреймворка
- **Валидация:** Алгоритм сам обрабатывает данные. Если данные не проходят внутренний пайплайн — возвращаем `422 Unprocessable Entity` с деталями из `meta.warnings`
- **Проверка заголовков на уровне шлюза:** НЕ требуется (алгоритм сам определяет и отклоняет некорректные данные)

### 3.2. Хранение промежуточных данных

- **Решение:** Сразу в реляционную БД (PostgreSQL)
- **Обоснование:**
  - Бизнес может открыть мини-апп с разных устройств
  - Нужна история изменений и версионность
  - Нужна фильтрация и пагинация для фронтенда
  - Файлы и in-memory хранилища не обеспечивают персистентность

### 3.3. Асинхронная обработка

- **Решение:** Только асинхронный подход через очередь задач
- **Обоснование:**
  - 200 000 строк — это секунды на расчёт, но нельзя блокировать HTTP-соединение
  - Мобильные клиенты (мини-апп) часто теряют соединение
  - Нужен прогресс-бар и повторные запросы статуса
- **Стек:** Redis + `arq` (лёгкий аналог Celery для MVP)

### 3.4. Редактирование — массовые правила для групп

- **Решение:** Бизнес редактирует бонус на уровне категории (3–27 карточек)
- **Обоснование:**
  - 200 000 строк невозможно редактировать вручную
  - Категории уже содержат агрегаты (средний чек, recency, count)
  - При подтверждении бэкенд применяет `final_bonus` категории ко всем её клиентам

### 3.5. Жизненный цикл бонусов

- **Решение:** State Machine с фоновым планировщиком
- **Механика:**
  - Стандартный TTL: 14 дней (редактируется бизнесом на уровне кампании)
  - За 2 дня до сгорания: push-уведомление клиенту через бота
  - В момент сгорания: вызов API лояльности на списание

### 4.2. Перечисления (Enums)

**campaign_status:**

- `PROCESSING` — CSV загружен, идёт расчёт
- `DRAFT` — расчёт завершён, бизнес просматривает
- `APPROVED` — бизнес подтвердил, идёт начисление
- `RUNNING` — бонусы начислены, кампания активна
- `COMPLETED` — все бонусы либо использованы, либо сгорели

**transaction_status:**

- `PENDING` — ожидает начисления в API лояльности
- `ACCRUED` — успешно начислено
- `USED` — клиент потратил (пришёл вебхук)
- `EXPIRED` — сгорело (списано планировщиком)
- `FAILED` — ошибка при начислении

**admin_role:**

- `owner` — полный доступ
- `viewer` — только просмотр

### 4.3. Ключевые индексы

```sql
-- Быстрый поиск транзакций для планировщика сгорания

CREATE INDEX idx_cat_campaign ON campaign_categories(campaign_id);
```

## 5. API Flow (Мини-апп и Бэкенд)

### 5.1. Авторизация

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/api/v1/auth/verify-max` | Валидация `initData` от MAX SDK, выдача JWT |

**Flow:**

1. Мини-апп открывается внутри бота MAX
2. MAX SDK передаёт на фронтенд подписанную строку `initData`
3. Фронтенд отправляет `initData` на бэкенд
4. Бэкенд проверяет подпись токеном бота, извлекает `user_id`
5. Сверяет с таблицей `business_admins`
6. Возвращает JWT-токен для дальнейших запросов

### 5.2. Кампании

| Метод | Путь | Описание |

| `PATCH` | `/api/v1/campaigns/{id}/categories/{cat_id}` | Изменение `final_bonus` для категории |
| `POST` | `/api/v1/campaigns/{id}/approve` | Подтверждение и запуск начисления |

### 5.3. Статистика

## 6. Внутренний Workflow системы

### 6.1. Полный цикл (от CSV до сгорания)

```
+------------------------------------------------------------------+
| ЭТАП 1: Загрузка и расчёт                                        |
+------------------------------------------------------------------+
|                                                                  |
|  Бизнес -> Мини-апп -> POST /upload                              |
|       |                                                          |
|       v                                                          |
|  Бэкенд сохраняет CSV на диск                                    |
|  Создаёт Campaign(status=PROCESSING) в БД                        |
|  Пушит задачу в Redis (arq)                                      |
|  Возвращает campaign_id                                          |
|       |                                                          |
|       v                                                          |
|  Worker: читает CSV -> pipeline.py -> рассчитывает метрики       |
|  Сохраняет категории в campaign_categories                       |
|  Меняет статус на DRAFT                                          |
|                                                                  |
+------------------------------------------------------------------+
                              |
                              v
+------------------------------------------------------------------+
| ЭТАП 2: Редактирование (Мини-апп)                                |
+------------------------------------------------------------------+
|                                                                  |
|  Бизнес видит 3-27 карточек категорий                            |
|  Меняет final_bonus для нужных категорий                         |
|  Каждый PATCH обновляет строку в БД                              |
|                                                                  |
+------------------------------------------------------------------+
                              |
                              v
+------------------------------------------------------------------+
| ЭТАП 3: Подтверждение и начисление                               |
+------------------------------------------------------------------+
|                                                                  |
|  Бизнес жмёт "Запустить" -> POST /approve                        |
|       |                                                          |
|       v                                                          |
|  Валидация: SUM(final_bonus * clients_count) <= budget?          |
|  Статус -> APPROVED                                              |
|       |                                                          |
|       v                                                          |
|  Worker: для каждой категории берёт client_ids                   |
|  Генерирует bonus_transactions (статус PENDING)                  |
|       |                                                          |
|       v                                                          |
|  Worker: батчами по 500 вызывает API Лояльности                  |
|  При успехе: статус -> ACCRUED, ставит expires_at               |
|  При ошибке: статус -> FAILED                                    |
|       |                                                          |
|       v                                                          |
|  Отправляет push через MAX Bot API каждому клиенту               |
|                                                                  |
+------------------------------------------------------------------+
                              |
                              v
+------------------------------------------------------------------+
| ЭТАП 4: Жизнь бонусов (14 дней)                                  |
+------------------------------------------------------------------+
|                                                                  |
|  День 12: Scheduler находит бонусы с <= 2 дней до сгорания       |
|           -> отправляет push "У вас сгорает 500 бонусов!"        |
|                                                                  |
|  День 14: Scheduler находит бонусы с expires_at <= NOW()         |
|           -> вызывает API Лояльности на списание (revoke)        |
|           -> статус -> EXPIRED                                   |
|                                                                  |
|  В любой момент: приходит Webhook от лояльности                  |
|           -> клиент потратил баллы                               |
|           -> статус -> USED                                      |
|                                                                  |
+------------------------------------------------------------------+
                              |
                              v
+------------------------------------------------------------------+
| ЭТАП 5: Отчётность                                               |
+------------------------------------------------------------------+
|                                                                  |
|  Раз в неделю бот присылает бизнесу текстовую сводку             |
|  По завершении кампании — итоговый отчёт                         |
|                                                                  |
+------------------------------------------------------------------+
```

### 6.2. Обработка ошибок на этапе начисления

```
Для каждого батча (500 клиентов):
  +-- Успех -> статус ACCRUED, сохраняем external_txn_id
  +-- Таймаут -> retry через 30 сек (максимум 3 попытки)
  +-- Ошибка 4хх -> статус FAILED, логируем
  +-- Ошибка 5хх -> retry через 60 сек
После всех батчей:
  +-- Отправляем бизнесу итог: "Начислено 185 000, ошибки: 2 420"
```

## 7. Интеграция с внешними системами

### 7.1. API Программы Лояльности

**Ожидаемые методы:**

| Метод | Назначение | Наш вызов |
|---|---|---|
| `POST /accrue` | Начислить баллы | При запуске кампании |
| `POST /revoke` | Списать баллы | При сгорании (день 14) |
| `GET /balance/{client_id}` | Проверить баланс | Опционально, для верификации |

## 8. Планировщик и жизненный цикл бонусов

### 8.1. Задачи планировщика

| Задача | Частота | Логика |
|---|---|---|
| Проверка сгорания | Каждый час | Найти `ACCRUED` с `expires_at <= NOW()` -> вызвать `revoke` -> статус `EXPIRED` |
| Напоминание о сгорании | Раз в сутки (10:00) | Найти `ACCRUED` с `expires_at <= NOW() + 2 days` и `reminder_sent=False` -> push -> `reminder_sent=True` |
| Еженедельный отчёт | Пн 09:00 | Агрегировать статистику -> отправить бизнесу в бота |
| Проверка FAILED | Каждые 5 минут | Повторить начисление для `FAILED` (максимум 3 попытки) |

### 8.2. TTL (время жизни бонусов)

- **По умолчанию:** 14 дней
- **Редактируемый:** бизнес может изменить при создании кампании
- **Хранение:** поле `ttl_days` в таблице `campaigns`
- **Расчёт:** `expires_at = accrued_at + INTERVAL '{ttl_days} days'`

### 8.3. State Machine транзакции

```
PENDING ──> ACCRUED ──> USED
   |            |
   |            +──────> EXPIRED
   |
   +──> FAILED ──> (retry) ──> PENDING
```

## Приложение А: Формулы расчёта бонусов

### Текущая формула скидки (из `discount_policy.py`):

```
need = 0.6 * r_norm + 0.4 * (1 - f_norm)
value = 0.6 * m_norm + 0.4 * f_norm
raw_discount = max_discount * need * (0.5 + 0.5 * value)
```

### Адаптация под бонусы:

```
need = 0.6 * r_norm + 0.4 * (1 - f_norm)
value = 0.6 * m_norm + 0.4 * f_norm
raw_bonus = max_bonus_points * need * (0.5 + 0.5 * value)
bonus = round_to_step(raw_bonus, step)
bonus = clamp(bonus, step, max_bonus_points)
```

### Параметры:

| Параметр | Значение по умолчанию | Описание |
|---|---|---|
| `max_bonus_points` | 1000 | Максимальный бонус для одной категории |
| `step` | 50 | Шаг округления (кратно 50 бонусам) |
| `need_free` | 0.25 | Ниже этого порога бонус не нужен |
| `value_cut` | 0.20 | Порог отсечения низкой ценности |
| `churn_bonus` | 50 | Минимальный бонус для отточного сегмента |

### Правила назначения (адаптированы из скидок):

| Условие | Поведение | Причина |
|---|---|---|
| `need <= need_free` | Бонус = 0 | Высокая естественная активность — бонус не нужен |
| `value <= value_cut` И `r_norm >= 0.5` | Бонус = `max(step, churn_bonus)` | Низкая ценность при оттоке — минимальный бонус последнего шанса |
| Остальные случаи | Бонус по формуле | Стимулирование спроса |

### Бюджет акции (адаптация):

```
budget = sum(avg_amount * bonus / 100 * response_rate)
```

Где `response_rate = 0.1` означает ожидаемый отклик 10%.
